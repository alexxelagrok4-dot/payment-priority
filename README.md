# ОБЯЗАТЕЛЬСТВА-ПЛАТЕЖИ

Инструмент для финансовой службы: реестр обязательств компании перед ключевыми контрагентами (поставщики оборудования, поставщики транспортных услуг, налоговая, залоги, подлежащие возврату клиентам, аренда/инфраструктура, зарплата и ФОТ, кредиты и займы) и приоритизация платежей — чтобы платежи, без которых бизнес остановится, не терялись среди множества мелких некритичных платежей, которые производятся регулярно и в сумме заметно утекают из кассы.

Файл `index.html` — самодостаточный (как и остальные инструменты компании), использует тот же Supabase-проект и тот же общий логин/пароль, что и «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — отдельного аккаунта заводить не нужно.

## v1: ручной ввод

Обязательства вносятся вручную по мере поступления счетов/требований. Схема данных сразу спроектирована с заделом под пакетную загрузку (поля `source`, `upload_batch_id`, таблица `pay_uploads`) — сама форма загрузки из 1С/Excel не реализована в этой версии и добавится отдельной итерацией, когда определится формат выгрузки (по аналогии с тем, как развивался инструмент СБ «Продление-Взыскание» — см. его `changelog/`).

## Экраны

1. **Реестр** — добавление обязательства (контрагент, категория, сумма, срок, признак «критично»), список с фильтрами по категории/критичности/статусу/контрагенту, отметка оплаты (полной или частичной — можно платить несколькими траншами), отмена и возврат в реестр.
2. **Очередь приоритизации** — открытые обязательства, критичные — первыми, внутри группы — по сроку. Сводка отдельно по критичным и некритичным: сколько открыто всего и сколько нужно к выбранной дате.
3. **Отчёт об утечках** — некритичные оплаты за период, сгруппированные по контрагенту и по категории, с количеством и суммой — чтобы увидеть, где мелкие регулярные платежи в сумме дают заметную утечку капитала.
4. **Динамика** — открытый остаток обязательств по каждой категории на конец последних 6 месяцев, с индикатором роста/снижения — растёт или гасится долг перед конкретным стейкхолдером.

## Модель критичности

Обязательство помечается «критично», если без его оплаты бизнес останавливается (например, срочный транспорт под текущий рейс, налоги с риском блокировки счёта). Всё остальное — некритичное: оно всё равно платится, но не должно требовать оплаты раньше критичного при ограниченной кассе. Статус «оплачено»/«частично» не хранится напрямую — вычисляется из фактических платежей (`pay_payments`), поле `status` в базе хранит только явную отмену (`cancelled`).

## Настройка базы (один раз)

Тот же Supabase-проект, что у остальных внутренних инструментов. В **SQL Editor** этого проекта выполнить [`supabase-setup.sql`](supabase-setup.sql) — скрипт идемпотентный, можно выполнять повторно.

## Вход

Тот же логин/пароль, что и в остальных внутренних инструментах компании (общий Supabase-проект, вход по логину без почты, синтетический email `логин@opalubka.invalid`).

## Что сознательно не сделано в этой версии

- **Пакетная загрузка файла** — только задел в схеме, форма не реализована.
- **Публичное зеркало на GitHub Pages** — заведём после того, как инструмент проверят вживую и он устоится, как это было сделано для `sb-debt-dynamics` и калькулятора аренды.
- **Разграничение доступа только для финслужбы** — используется общий вход всех внутренних инструментов; отдельная роль — будущая доработка, если понадобится.
