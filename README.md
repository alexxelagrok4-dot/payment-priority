# Дайя-Финансы

Инструмент управления ликвидностью для финансовой службы: структура и динамика обязательств и поступлений компании, приоритизация платежей по реальной цене неоплаты, бюджет расходов и доходов с историей корректировок, ежедневная кассовая позиция, обнаружение кассовых разрывов и прогноз исполнения бюджета на конец месяца методом экстраполяции — ДДС на кассовой основе. Вырос из простого «реестра платежей на согласование» — назначение и экраны описаны ниже целиком, без деления на «было/стало». Изначально назывался «Обязательства-Платежи»; переименован в «Дайя-Финансы» и оформлен в фирменном стиле Дайя Групп (цвета/шрифт сайта dayagroup.ru) — единственный инструмент серии с таким оформлением, остальные (ПРОДЛЕНИЕ-ВЗЫСКАНИЕ, СКЛАД-РЕМОНТ, ДАШБОРД-РУКОВОДСТВА) остаются на общем нейтральном стиле.

Файл `index.html` — самодостаточный (как и остальные инструменты компании), использует тот же Supabase-проект и тот же общий логин/пароль, что и «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — отдельного аккаунта заводить не нужно.

## Экраны

Шесть вкладок: **Дашборд** (главная страница, открывается первой), **Реестр**
(+ согласование внутри него), **Бюджет**, **Прогноз**, **Приоритеты статей**,
**Импорт**. Аналитика — не отдельные вкладки, а drill-down с дашборда: от
общей цифры кликами вглубь до конкретного платежа («от общего к частному, от
следствия к причине»), а не переключение между листами.

1. **Дашборд** — два крупных кликабельных показателя:
   - **Обязательства всего** (открытый остаток) → клик → 4 приоритета
     (Критичный/Важный операционный/Операционный/Низкий, с предупреждением о
     кассовом разрыве, если доступных денег не хватает на критичное) → клик
     по приоритету → статьи внутри него → клик по статье → контрагенты
     внутри статьи (открытый остаток по каждому). Хлебные крошки сверху
     позволяют вернуться на любой пройденный уровень.
   - **Эффективность использования денежных средств** — коэффициент за
     период (по умолчанию с 1-го числа текущего месяца по сегодня, дата
     меняется на самом экране) → клик → статьи потерь за период,
     отсортированные по убыванию → клик по статье → сами платежи (кому, за
     что, сколько, когда). Формула и веса — см. «Эффективность» ниже.

   Кнопка «Перейти к реестру платежей» переключает на «Реестр». Ниже двух
   показателей — три вторичные панели, не входящие в drill-down (данные
   нужны, но они не укладываются в одну из двух воронок выше): **Итоги
   периода** (неделя/месяц — сколько оплачено, разбивка по приоритету и
   статьям), **Динамика** (открытый остаток по статьям и приоритету на конец
   последних 6 месяцев), **Сравнение периодов** («на начало»/«на конец»,
   изменение в ₽ и % по приоритету и по статьям; форма «Сохранить как
   известный остаток» — ручной оверрайд, когда в реестре ещё нет полной
   истории на нужную дату).
2. **Реестр** — рабочее место оператора. Для роли admin сверху —
   секция **«Согласование»** (не отдельная вкладка): очередь обязательств на
   решение (согласование по одной записи или пакетом), заявки на оплату
   приоритета «Низкий» (утвердить целиком/с урезанием суммы или отклонить,
   см. «Оплата приоритета «Низкий»» ниже), история обоих. Счётчик ожидающих
   — бейджем прямо на кнопке вкладки «Реестр». Ниже — «Касса сегодня»
   (остаток на начало дня + поступления за вчера). Форма «Новое
   обязательство» — сумма → контрагент → статья (тип подставляется сам, см.
   «Приоритизация»), Enter отправляет, статья/срок не сбрасываются между
   вводами (частый случай — несколько платежей подряд по одной статье). К
   форме можно приложить сам счёт на оплату (PDF или скан) — см. «Счёт на
   оплату» ниже. Список обязательств — фильтры по статье/типу/статусу/
   контрагенту/согласованию; статья и тип редактируются прямо в таблице.
   Оплата — полная или частичная, несколькими траншами; у обязательства с
   оплатами — ссылка «оплат: N — показать/удалить» с историей и удалением
   каждой. У приоритета «Низкий» вместо оплаты — «Запросить оплату» для
   оператора, для остальных приоритетов оплата проводится напрямую как
   обычно. Кнопка «Удалить» у строки полностью убирает обязательство
   безвозвратно (с оплатами) — отдельно от «Отменить» (обратимо, кнопкой
   «Вернуть»).
3. **Бюджет** — сверху сводка «план/факт: доходы − расходы» (net), ниже —
   два одинаково устроенных блока, «Расходы» и «Доходы»: первоначальный план
   (эталон, не меняется), текущий план (правится прямо в таблице — каждое
   изменение требует причины и попадает в историю, клик по «Корректировка»
   её показывает), факт (реально оплачено/получено по статье в этом
   месяце), отклонение факта от плана. Статьи без плана на месяц — с кнопкой
   «Задать план». Если строка пришла из импорта с несколькими исходными
   позициями — название статьи кликабельно и разворачивает список этих
   позиций.
4. **Прогноз** — прогноз исполнения бюджета на конец выбранного месяца:
   простая линейная экстраполяция (факт на сегодня ÷ прошедшие дни месяца ×
   дни в месяце), отдельно по доходам и расходам и по статьям внутри них, с
   прогнозным профицитом/дефицитом относительно плана и отклонением факта от
   плана на текущую дату. Это ДДС на кассовой основе (по факту движения
   денег) — не ОПиУ (по начислению), см. «ДДС, а не ОПиУ — почему» ниже.
5. **Приоритеты статей** — справочник статей расходов (добавление,
   приоритет по умолчанию, переименование, удаление) и отдельно справочник
   статей дохода (то же самое, но без приоритета — у дохода нет смысловой
   «критичности неполучения»).
6. **Импорт** — общее меню всех шести слотов загрузки в одном месте, у
   каждого свой файл/вставка из буфера и своё сопоставление колонок (Excel
   `.xlsx`/`.xls`/`.csv`, формат заранее не подгонялся — колонки в любом
   порядке и с любыми названиями; разбор идёт целиком в браузере —
   `xlsx.js`/SheetJS с CDN, сам файл на сервер не уходит, только разобранные
   строки):
   - **Загрузить кредиторскую задолженность** — обязательства перед контрагентами. Статья необязательна — без неё строки получают «Не распределено», разбираются потом в «Реестре». Обязательства можно заносить и так (пакетно, из документа), и вручную по одному через форму «Новое обязательство» в «Реестре» — оба способа равноправны, ничего не обязывает выбрать один.
   - **Загрузить бюджет** — план расходов на выбранный месяц. Несколько строк файла с одной статьёй складываются в план по этой статье, а исходные строки сохраняются как позиции (видны при клике на статью в «Бюджете»). Если в файле есть статьи, которых нет в справочнике, — на шаге сопоставления для каждой явно выбирается «создать новую» или «переименовать существующую статью в это название» (переименование каскадно применяется в обязательствах, бюджете и справочнике, см. «Переименование статьи»). Уже созданный на этот месяц план по статье повторным импортом не перезаписывается (строка пропускается).
   - **Загрузить реестр платежей** — уже сделанные оплаты (факт). Каждая строка становится обязательством, сразу закрытым этой же оплатой — так исторические платежи попадают в «Итоги периода», «Эффективность» и «Динамику» на дашборде и в «Прогноз», даже если они случились до перехода на инструмент.
   - **Загрузить кассовую позицию по дням** — пакетно, если остаток/поступления ведутся отдельным файлом; на существующую дату значение обновляется, а не задваивается.
   - **Загрузить поступления** — факт прихода денег, с привязкой к дате поступления и (необязательно) статьёй и источником/плательщиком.
   - **Загрузить бюджет доходов** — план доходов на месяц, той же механикой группировки по статье и переименования, что и «Загрузить бюджет» — только для статей дохода (`pay_income_categories`, отдельный справочник без приоритета).

   Каждая из этих шести форм — единственный физический экземпляр (одна и та же логика, одни и те же поля), но на страницах «Реестр», «Бюджет» и «Прогноз» соответствующая форма дополнительно появляется прямо в контексте страницы — не копия, а тот же элемент, перемещённый в вёрстке на время, пока открыта эта вкладка (при уходе обратно на «Импорт» все шесть снова собраны в общем меню, в исходном порядке). Так на «Реестре» под рукой загрузка кредиторки/платежей/кассы, на «Бюджете» — загрузка бюджета расходов/доходов, на «Прогнозе» — загрузка поступлений, без необходимости уходить с рабочей страницы в «Импорт» и обратно.

   У каждой формы — кнопка «Очистить»: убирает выбранный файл, вставленный текст и уже разобранное сопоставление колонок, только после явного подтверждения (несохранённый черновик загрузки теряется без возможности восстановить). На уже импортированные данные (то, что реально попало в базу до нажатия «Импортировать») кнопка не действует — их удаление делается на той странице, где эти данные видны (обязательство/платёж — в «Реестре», статья бюджета — в «Бюджете» и т.д.), тем же принципом подтверждения перед удалением, что и везде в инструменте.

   Реальные отчёты часто выгружаются не в виде простой таблицы «заголовок в первой строке, дальше данные» — например, месячный CFS-отчёт с несколькими строками шапки (подписи, факт/план, остаток на начало) перед самими статьями. Для этого у каждой формы — поля «Строка заголовков» и «Первая строка данных» (по умолчанию 1 и 2 — как было раньше, для простых файлов ничего менять не нужно): указываете, с какой строки файла реально начинаются нужные заголовки колонок и сами данные, жмёте «Обновить» — сопоставление и превью пересчитываются от этих строк. Нумерация не учитывает полностью пустые строки файла (они пропускаются при разборе).

   В превью у каждой строки — чекбокс (плюс «выбрать все» в шапке): по умолчанию все отмечены, снятая галочка исключает строку из импорта. Это нужно, когда в файле вперемешку со строками-статьями есть итоговые/групповые строки (например, «ИТОГО РАСХОДОВ», «Чистые потоки ДС к распределению») — их нельзя отличить от обычных статей программно надёжно, поэтому решение — за оператором: вычеркнуть такие строки перед подтверждением импорта, иначе они задвоят итоги бюджета (сумма группы уже включает суммы её строк). Суммы для «Загрузить бюджет»/«Загрузить бюджет доходов» всегда берутся по модулю — если расходы и доходы в файле записаны в одной колонке со знаком (расход отрицательным числом), это не мешает: делаете два прохода тем же файлом — один раз в «Загрузить бюджет», вычеркнув строки дохода, второй раз в «Загрузить бюджет доходов», вычеркнув расход.

## Эффективность использования денежных средств

Показатель на дашборде, отвечает на вопрос «какая доля потраченного была
оправдана делом, а не утекла на некритичное». Каждому приоритету — вес от 0
до 100% (насколько оправдана трата по нему):

| Приоритет | Вес |
|---|---|
| Критичный | 100% |
| Важный операционный | 90% |
| Операционный | 70% |
| Низкий | 0% |

Коэффициент за период = Σ(платёж × вес приоритета) / Σ(платёж) — доля
потраченного оправданно. Потери = Σ платёж × (1 − вес приоритета) —
раскладываются по статьям и по самим платежам при drill-down с дашборда.
Приоритет «Низкий» с весом 0% — частный случай, полностью «утечка»; веса
90%/70% для важного операционного/операционного признают, что не всё
некритичное — потеря, лишь часть. Веса — константа в коде
(`TIER_EFFICIENCY_WEIGHT`), не редактируются через интерфейс в этой версии.

## Приоритизация: по цене неоплаты, а не по типу расхода

- **Критичный** — деятельность серьёзно пострадает/остановится за несколько дней: блокировка счёта налоговой, трудовая инспекция за задержку зарплаты, демонтаж/утрата оборудования, логистика вывоза при риске утраты.
- **Важный операционный** — не остановит бизнес, но падает производительность/утилизация: маркетинг, расходники для ремонта, топливо для СБ, клиентские залоги, логистика доставки клиенту.
- **Операционный** — относится к основной деятельности, критичных последствий в горизонте 30 дней нет.
- **Низкий приоритет** — не относится к основной деятельности; вес 0% в «Эффективности использования денежных средств» на дашборде — источник основных потерь.

Список статей и приоритет по умолчанию для каждой целиком живут в `pay_category_priorities` (вкладка «Приоритеты статей», без правки кода). Приоритет конкретного обязательства можно переопределить в «Реестре», если оно выбивается из общего правила статьи. Статус «оплачено»/«частично» не хранится напрямую — вычисляется из `pay_payments`; поле `status` хранит только явную отмену (`cancelled`).

## Переименование статьи

Кнопка «Переименовать» на «Приоритеты статей» — новое название применяется каскадно везде: в справочнике (переносит приоритет на новое имя), во всех обязательствах (`pay_obligations.category`) и во всех строках бюджета (`pay_budget_lines.category`); старое название из справочника удаляется. Это не «мягкое» переименование — история не остаётся под старым именем, вся привязана к новому. То же самое происходит автоматически при импорте бюджета, если для статьи файла, которой нет в справочнике, выбрать «переименовать существующую статью в это название» вместо «создать новую» (см. «Импорт» выше) — так после загрузки бюджета названия статей в инструменте синхронизируются с тем, как они называются в исходном файле. У статей дохода — то же самое, отдельным механизмом (`pay_income_categories`/`pay_receipts`/`pay_income_budget_lines`), не связанным со статьями расходов.

## Счёт на оплату

К форме «Новое обязательство» в «Реестре» можно приложить файл счёта на оплату (PDF или скан-изображение). Для PDF с текстовым слоем инструмент пробует сам прочитать сумму и контрагента (`pdf.js`, разбор целиком в браузере) и подставляет их в поля формы — но только если поле ещё пустое, руками введённое не перезаписывается. Распознавание приблизительное (ищет фразы вида «итого к оплате»/«получатель» в тексте счёта) и **всегда требует проверки перед сохранением** — это подсказка, а не источник истины. Для скан-изображений (JPG/PNG) и PDF без текстового слоя (отсканированные счета) автораспознавание не работает — файл просто прикладывается, сумма/контрагент вводятся вручную.

Сам файл сохраняется в приватный Storage-бакет `invoices` (не публичный — доступ только по подписанной ссылке, действующей 60 секунд, для залогиненного сотрудника). После добавления обязательства с приложенным счётом в «Реестре» рядом с контрагентом появляется ссылка «счёт», открывающая файл.

## ДДС, а не ОПиУ — почему

Вкладка «Прогноз» и весь инструмент вообще считают деньги **по факту движения** (когда пришло/ушло) — это отчёт о движении денежных средств (ДДС). Отчёт о прибылях и убытках (ОПиУ) считает по **моменту начисления** (когда выручка/расход признаны экономически, что может отличаться от даты оплаты) — для этого нужна отдельная дата признания на каждую операцию, которую инструмент сейчас не собирает нигде. Это осознанное решение по объёму, не недосмотр: кассовая модель уже покрывает главные вопросы («хватит ли денег», «сколько реально потратили/получили», «какой прогноз к концу месяца»), а переход на начисление — отдельная, более крупная задача с другой моделью данных.

## Кассовая позиция и бюджет — как они связаны

Кассовая позиция (сколько денег реально есть сегодня) — не то же самое, что бюджет (сколько планировали потратить за месяц). Первая отвечает «хватит ли денег на критичное сегодня» (видно в «Очереди приоритизации»), второй — «сколько мы вообще собирались тратить по этой статье и насколько разъехался план» (видно на «Бюджете»). Обе цифры **не** блокируют друг друга и не блокируют согласование — это независимые контуры контроля поверх одного и того же реестра обязательств.

## Роли: просмотр, оператор, админ — с защитой на уровне базы

Каждый сотрудник входит под своим отдельным логином (общий у всех инструментов компании — Supabase-проект, а не единый пароль на всех). Роль **зашита в токене пользователя** (`app_metadata.role` в `auth.users`) и приходит вместе с сессией в момент входа — известна сразу при авторизации, а не проверяется отдельным запросом к базе постфактум. Три уровня:

| Роль | Значение `role` | Может |
|---|---|---|
| Просмотр | `viewer` | Видеть всё (все вкладки, включая секцию «Согласование» в «Реестре», дашборд, все отчёты) — ничего не вносить и не менять. |
| Оператор | не задана (по умолчанию) | Готовить реестр, вносить и корректировать данные (обязательства, оплаты, кассовая позиция, бюджет, импорт и т.д.). Провести оплату напрямую может по любому приоритету, **кроме «Низкий»** — для него доступна только «Запросить оплату» (см. ниже). |
| Админ | `admin` | Всё то же, что оператор, плюс: видит секцию «Согласование» в «Реестре», согласовывает/отклоняет обязательства, утверждает или отклоняет заявки на оплату по приоритету «Низкий» (может урезать запрошенную сумму), может провести оплату по любому приоритету напрямую. |

В отличие от более ранней версии, где кнопки просто скрывались по роли в интерфейсе, все три уровня **закреплены в RLS-политиках самой базы** (`app_role()` в `supabase-setup.sql`, читает роль из JWT так же, как и клиент): попытка вставить/изменить/удалить что-либо в обход интерфейса (напрямую через Supabase-клиент) получит `permission denied`, если роль этого не позволяет. Это касается и роли `viewer` (читает всё, не пишет ничего), и шлюза на оплату низкоприоритетных обязательств (см. ниже) — оба реализованы в базе, а не только скрытием элементов в UI.

Каждое новое обязательство создаётся со статусом `pending`. Согласование обязательства — отдельный контур контроля, не шлюз: обязательство сразу видно во всех остальных экранах независимо от статуса согласования (в отличие от оплаты низкоприоритетных обязательств — это уже настоящий шлюз, см. ниже).

**Назначить роль** (разово на человека, доступ к SQL Editor Supabase-проекта — в интерфейсе инструмента этого действия намеренно нет, чтобы роль нельзя было выдать себе самому):

1. Человек должен хотя бы раз войти в инструмент своим логином.
2. В SQL Editor выполнить, подставив его логин (админ):
   ```sql
   update auth.users
   set raw_app_meta_data = raw_app_meta_data || jsonb_build_object('role', 'admin')
   where email = '<логин>@opalubka.invalid';
   ```
   или просмотр:
   ```sql
   update auth.users
   set raw_app_meta_data = raw_app_meta_data || jsonb_build_object('role', 'viewer')
   where email = '<логин>@opalubka.invalid';
   ```
3. Роль будет видна при следующем входе (уже открытая сессия подхватывает роль не мгновенно — токен переиздаётся при обновлении сессии).

Снять роль (вернуть в операторы) — тот же запрос с `raw_app_meta_data - 'role'` вместо `||`.

## Оплата приоритета «Низкий» — только через заявку

Это единственный реальный шлюз на движение денег в инструменте (в отличие от согласования обязательств выше, которое не блокирует). Приоритет «Низкий» — по определению то, что не относится к основной деятельности, вес 0% в «Эффективности использования денежных средств» на дашборде (см. «Приоритизация» выше); именно эта категория регулярно «пролетает незамеченной» мелкими суммами — ради защиты от неё и введён шлюз. Остальные три приоритета (Критичный/Важный операционный/Операционный) оператор проводит напрямую, как и раньше — их блокировать нельзя, это то, что должно платиться без задержек.

Как это выглядит: в «Реестре» у обязательства с приоритетом «Низкий» вместо кнопки «Оплатить» у оператора — «Запросить оплату» (сумма та же, вводится так же). Заявка попадает в секцию «Согласование» → «Заявки на оплату» (в «Реестре», видна только админу), где админ видит контрагента, статью, запрошенную сумму и может:

- **Утвердить** — по умолчанию на всю запрошенную сумму, но поле редактируемое: если ввести сумму меньше запрошенной, платёж проведётся на неё («режет» платёж), а остаток обязательства снова открыт (можно запросить оплату остатка отдельно).
- **Отклонить** — с необязательной причиной; платёж не создаётся.

Пока заявка ожидает решения, в «Реестре» на месте кнопки — бейдж «на согласовании: N ₽» (чтобы не плодить дубли заявок по одному обязательству). История решений — там же, в секции «Согласование».

Админ видит «Оплатить» напрямую всегда, включая приоритет «Низкий» — заявка нужна только когда оплату проводит не тот, кто её же и утверждает.

## Что сознательно не сделано в этой версии

- **Прямая интеграция с 1С (API)** — импорт работает через файл/буфер обмена (см. «Импорт»), а не через выгрузку/API напрямую; формат 1С-выгрузки заранее неизвестен, поэтому парсер универсальный (сопоставление колонок вручную), а не завязан на конкретную структуру.
- **Разграничение доступа только для финслужбы** — открыть инструмент может любой сотрудник с логином в общем Supabase-проекте компании; роли оператор/CEO-CFO уже есть внутри инструмента, но входа именно для финслужбы отдельно от остальной компании нет.
- **Уведомления** — ни о новых обязательствах на согласование, ни о кассовых разрывах push/email не приходят; всё видно только при заходе в соответствующий экран (для согласования — есть счётчик рядом с названием вкладки).
- **Бюджет по контрагентам** — план строится только по статьям, не по отдельным контрагентам внутри статьи.
- **ОПиУ (по начислению)** — сознательно не строим, см. «ДДС, а не ОПиУ — почему» выше.
- **Экстраполяция с учётом сезонности** — прогноз в «Прогнозе» линейный (факт на дату ÷ прошедшие дни × дни в месяце), без поправки на неравномерность поступлений/выплат внутри месяца.
- **Веса приоритетов для «Эффективности»** — правятся только в коде (`TIER_EFFICIENCY_WEIGHT`), без экрана настройки; список конкретных обязательств «к оплате по сроку в ближайшие N дней» (был на прежней отдельной вкладке «Очередь приоритизации») тоже не перенесён на дашборд как отдельная таблица — по сроку платежи уже видны в «Реестре» (колонка «Срок», фильтры), дублировать не стали, чтобы не плодить лишние экраны.
