# ОБЯЗАТЕЛЬСТВА-ПЛАТЕЖИ

Инструмент управления ликвидностью для финансовой службы: структура и динамика обязательств компании перед контрагентами, приоритизация платежей по реальной цене неоплаты, месячный бюджет с историей корректировок, ежедневная кассовая позиция и обнаружение кассовых разрывов. Вырос из простого «реестра платежей на согласование» — назначение и экраны описаны ниже целиком, без деления на «было/стало».

Файл `index.html` — самодостаточный (как и остальные инструменты компании), использует тот же Supabase-проект и тот же общий логин/пароль, что и «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — отдельного аккаунта заводить не нужно.

## Экраны

1. **Реестр** — рабочее место оператора. Сверху — «Касса сегодня» (остаток на начало дня + поступления за вчера, см. «Кассовая позиция» ниже). Форма «Новое обязательство» — сумма → контрагент → статья (тип подставляется сам, см. «Приоритизация»), Enter отправляет, статья/срок не сбрасываются между вводами (частый случай — несколько платежей подряд по одной статье). Список обязательств — фильтры по статье/типу/статусу/контрагенту/согласованию; статья и тип редактируются прямо в таблице (нужно для разбора импортированных обязательств и для ретегирования старых записей). Оплата — полная или частичная, несколькими траншами; у обязательства с оплатами — ссылка «оплат: N — показать/удалить» с историей и удалением каждой. Кнопка «Удалить» у строки полностью убирает обязательство безвозвратно (с оплатами) — отдельно от «Отменить» (обратимо, кнопкой «Вернуть»).
2. **Импорт** — четыре независимых слота загрузки, у каждого свой файл/вставка из буфера и своё сопоставление колонок (Excel `.xlsx`/`.xls`/`.csv`, формат заранее не подгонялся — колонки в любом порядке и с любыми названиями; разбор идёт целиком в браузере — `xlsx.js`/SheetJS с CDN, сам файл на сервер не уходит, только разобранные строки):
   - **Загрузить кредиторскую задолженность** — обязательства перед контрагентами (то же, что раньше называлось просто «Импорт»). Статья необязательна — без неё строки получают «Не распределено», разбираются потом в «Реестре».
   - **Загрузить бюджет** — план на выбранный месяц. Несколько строк файла с одной статьёй складываются в план по этой статье, а исходные строки сохраняются как позиции (видны при клике на статью в «Бюджете», см. ниже). Если в файле есть статьи, которых нет в справочнике, — на шаге сопоставления для каждой явно выбирается «создать новую» или «переименовать существующую статью в это название» (переименование каскадно применяется в обязательствах, бюджете и справочнике, см. «Переименование статьи»). Уже созданный на этот месяц план по статье повторным импортом не перезаписывается (строка пропускается).
   - **Загрузить реестр платежей** — уже сделанные оплаты (факт). Каждая строка становится обязательством, сразу закрытым этой же оплатой — так исторические платежи попадают в «Итоги периода», «Утечки» и «Динамику», даже если они случились до перехода на инструмент.
   - **Загрузить кассовую позицию по дням** — пакетно, если остаток/поступления ведутся отдельным файлом; на существующую дату значение обновляется, а не задваивается.
3. **Структура обязательств** — сколько всего открыто сейчас, разбивка по типу платежа и по статьям (сумма и % от общего, клик по статье — контрагенты внутри неё), топ-10 контрагентов по остатку. Ниже — **сравнение периодов**: «на начало»/«на конец», изменение в ₽ и %, разбивка по статьям с крупнейшими изменениями сверху. Если в реестре ещё нет полной истории на нужную дату — форма «Сохранить как известный остаток» задаёт его вручную (по статье или «Итого»), и он подставляется в расчёт сравнения вместо (неполного) факта из реестра.
4. **Очередь приоритизации** — открытые обязательства четырьмя группами по приоритету (см. ниже), внутри группы — по сроку. Сверху — «Доступно сегодня» (последняя сохранённая кассовая позиция) с явным предупреждением, если этого не хватает на сумму критичных обязательств — прямое обнаружение кассового разрыва.
5. **Бюджет** — план по статьям на выбранный месяц: первоначальный план (эталон, не меняется), текущий план (правится прямо в таблице — каждое изменение требует причины и попадает в историю, клик по «Корректировка» её показывает), факт (реально оплачено по статье в этом месяце), отклонение факта от плана. Статьи без плана на месяц — с кнопкой «Задать план». Если строка пришла из импорта с несколькими исходными позициями — название статьи кликабельно и разворачивает список этих позиций (клик по статье в реестре — от общего плана к частным подпунктам, из которых он собран).
6. **Итоги периода** — неделя/месяц: сколько всего оплачено, разбивка по приоритету и расход по статьям.
7. **Отчёт об утечках** — оплаты низкого приоритета за произвольный период, по контрагенту и по статье.
8. **Динамика** — открытый остаток по статьям и по приоритету на конец последних 6 месяцев (помесячный тренд; для точечного сравнения двух дат — «Структура обязательств»).
9. **Приоритеты статей** — справочник статей целиком: добавление, изменение приоритета по умолчанию, переименование (см. ниже), удаление (не трогает уже созданные обязательства — они просто перестают предлагаться для новых).
10. **Согласование** — только для роли CEO/CFO (см. «Роли»): очередь на решение, согласование по одной записи или пакетом, история решений.

## Приоритизация: по цене неоплаты, а не по типу расхода

- **Критичный** — деятельность серьёзно пострадает/остановится за несколько дней: блокировка счёта налоговой, трудовая инспекция за задержку зарплаты, демонтаж/утрата оборудования, логистика вывоза при риске утраты.
- **Важный операционный** — не остановит бизнес, но падает производительность/утилизация: маркетинг, расходники для ремонта, топливо для СБ, клиентские залоги, логистика доставки клиенту.
- **Операционный** — относится к основной деятельности, критичных последствий в горизонте 30 дней нет.
- **Низкий приоритет** — не относится к основной деятельности; источник данных для «Отчёта об утечках».

Список статей и приоритет по умолчанию для каждой целиком живут в `pay_category_priorities` (вкладка «Приоритеты статей», без правки кода). Приоритет конкретного обязательства можно переопределить в «Реестре», если оно выбивается из общего правила статьи. Статус «оплачено»/«частично» не хранится напрямую — вычисляется из `pay_payments`; поле `status` хранит только явную отмену (`cancelled`).

## Переименование статьи

Кнопка «Переименовать» на «Приоритеты статей» — новое название применяется каскадно везде: в справочнике (переносит приоритет на новое имя), во всех обязательствах (`pay_obligations.category`) и во всех строках бюджета (`pay_budget_lines.category`); старое название из справочника удаляется. Это не «мягкое» переименование — история не остаётся под старым именем, вся привязана к новому. То же самое происходит автоматически при импорте бюджета, если для статьи файла, которой нет в справочнике, выбрать «переименовать существующую статью в это название» вместо «создать новую» (см. «Импорт» выше) — так после загрузки бюджета названия статей в инструменте синхронизируются с тем, как они называются в исходном файле.

## Кассовая позиция и бюджет — как они связаны

Кассовая позиция (сколько денег реально есть сегодня) — не то же самое, что бюджет (сколько планировали потратить за месяц). Первая отвечает «хватит ли денег на критичное сегодня» (видно в «Очереди приоритизации»), второй — «сколько мы вообще собирались тратить по этой статье и насколько разъехался план» (видно на «Бюджете»). Обе цифры **не** блокируют друг друга и не блокируют согласование — это независимые контуры контроля поверх одного и того же реестра обязательств.

## Роли: оператор и согласующий (CEO/CFO)

Каждый сотрудник входит под своим отдельным логином (общий у всех инструментов компании — Supabase-проект, а не единый пароль на всех). Роль **зашита в токене пользователя** (`app_metadata.role` в `auth.users`) и приходит вместе с сессией в момент входа — известна сразу при авторизации, а не проверяется отдельным запросом к базе постфактум:

- **Оператор** (по умолчанию) — вносит обязательства, оплаты, кассовую позицию; видит статус согласования каждой своей записи, но вкладки «Согласование» не видит.
- **CEO/CFO** (`role = 'approver'`) — дополнительно видит «Согласование»: очередь на решение, согласование по одной записи или пакетом (чекбоксы + «Согласовать выбранное»).

Каждое новое обязательство создаётся со статусом `pending`. Согласование — отдельный контур контроля, не шлюз: обязательство сразу видно во всех остальных экранах независимо от статуса согласования.

**Назначить согласующего** (разово на человека, доступ к SQL Editor Supabase-проекта — в интерфейсе инструмента этого действия намеренно нет, чтобы роль нельзя было выдать себе самому):

1. Человек должен хотя бы раз войти в инструмент своим логином.
2. В SQL Editor выполнить, подставив его логин:
   ```sql
   update auth.users
   set raw_app_meta_data = raw_app_meta_data || jsonb_build_object('role', 'approver')
   where email = '<логин>@opalubka.invalid';
   ```
3. Вкладка «Согласование» появится при следующем входе (уже открытая сессия подхватывает роль не мгновенно — токен переиздаётся при обновлении сессии).

Снять роль — тот же запрос с `raw_app_meta_data - 'role'` вместо `||`. Права в базе на согласование не разграничены строже, чем у остальных действий инструмента (тот же принцип «доверяем всем залогиненным сотрудникам», что и в остальных инструментах DAYA) — кнопки скрыты в интерфейсе для не-согласующих, но это ограничение на уровне UI, не базы.

## Настройка базы (один раз, и при каждом обновлении схемы)

Тот же Supabase-проект, что у остальных внутренних инструментов. В **SQL Editor** этого проекта выполнить [`supabase-setup.sql`](supabase-setup.sql) целиком — скрипт идемпотентный, можно выполнять повторно, порядок операций специально выстроен так, чтобы миграции колонок/данных всегда шли раньше операций, которые от них зависят (индексы, новые таблицы).

## Вход

Тот же логин/пароль, что и в остальных внутренних инструментах компании (общий Supabase-проект, вход по логину без почты, синтетический email `логин@opalubka.invalid`).

## Что сознательно не сделано в этой версии

- **Прямая интеграция с 1С (API)** — импорт работает через файл/буфер обмена (см. «Импорт»), а не через выгрузку/API напрямую; формат 1С-выгрузки заранее неизвестен, поэтому парсер универсальный (сопоставление колонок вручную), а не завязан на конкретную структуру.
- **Разграничение доступа только для финслужбы** — открыть инструмент может любой сотрудник с логином в общем Supabase-проекте компании; роли оператор/CEO-CFO уже есть внутри инструмента, но входа именно для финслужбы отдельно от остальной компании нет.
- **Уведомления** — ни о новых обязательствах на согласование, ни о кассовых разрывах push/email не приходят; всё видно только при заходе в соответствующий экран (для согласования — есть счётчик рядом с названием вкладки).
- **Бюджет по контрагентам** — план строится только по статьям, не по отдельным контрагентам внутри статьи.
