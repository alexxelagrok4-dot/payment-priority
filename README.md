# ОБЯЗАТЕЛЬСТВА-ПЛАТЕЖИ

Инструмент для финансовой службы: реестр обязательств компании перед ключевыми контрагентами (поставщики оборудования, поставщики транспортных услуг, налоговая, залоги, подлежащие возврату клиентам, аренда/инфраструктура, зарплата и ФОТ, кредиты и займы) и приоритизация платежей — чтобы платежи, без которых бизнес остановится, не терялись среди множества мелких некритичных платежей, которые производятся регулярно и в сумме заметно утекают из кассы.

Файл `index.html` — самодостаточный (как и остальные инструменты компании), использует тот же Supabase-проект и тот же общий логин/пароль, что и «ПРОДЛЕНИЕ-ВЗЫСКАНИЕ» — отдельного аккаунта заводить не нужно.

## v1: ручной ввод

Реестр формируется вручную, обычно ежедневно, по мере поступления счетов/требований — форма ввода рассчитана именно на такой темп (см. «Ежедневный ввод» ниже). Схема данных сразу спроектирована с заделом под пакетную загрузку (поля `source`, `upload_batch_id`, таблица `pay_uploads`) — сама форма загрузки из 1С/Excel не реализована в этой версии и добавится отдельной итерацией, когда определится формат выгрузки (по аналогии с тем, как развивался инструмент СБ «Продление-Взыскание» — см. его `changelog/`).

## Экраны

1. **Реестр** — добавление обязательства (сумма, контрагент, статья — тип проставляется автоматически по статье), список с фильтрами по статье/типу/статусу/контрагенту/согласованию, отметка оплаты (полной или частичной — можно платить несколькими траншами), отмена и возврат в реестр. По каждому обязательству с хотя бы одной оплатой — ссылка «оплат: N — показать/удалить»: раскрывает список оплат с датой/суммой/автором и кнопкой «Удалить» на каждую (статус обязательства пересчитывается автоматически). Кнопка «Удалить» у каждой строки полностью убирает обязательство из реестра (с подтверждением, безвозвратно — вместе с ним удаляются и его оплаты) — это отдельное действие от «Отменить», которое лишь меняет статус и его можно вернуть кнопкой «Вернуть».
2. **Структура обязательств** — «фото» текущего состояния: сколько всего открыто, разбивка по типу платежа и по статьям (сумма и % от общего), топ-10 контрагентов по открытому остатку. Ниже на этой же вкладке — **сравнение периодов**: выбираете «на начало» и «на конец», видите обязательства на каждую дату, изменение в рублях и в процентах, и разбивку по статьям с крупнейшими изменениями сверху — прямой ответ на «выросли обязательства или сократились» и на что именно.
3. **Очередь приоритизации** — открытые обязательства тремя группами: Базовые → Рост → Нерелевантные, внутри группы — по сроку. Сводка по каждой группе: сколько открыто всего и сколько нужно к выбранной дате.
4. **Итоги периода** — план/факт за выбранную неделю или месяц: сколько всего оплачено, разбивка по Базовые/Рост/Нерелевантные (утечки) и расход по статьям — один экран с ответом «сколько и на что потратили».
5. **Отчёт об утечках** — оплаты по нерелевантным обязательствам за произвольный период, сгруппированные по контрагенту и по статье, с количеством и суммой — детальный разбор утечек по контрагентам (в дополнение к сводке на «Итогах периода»).
6. **Динамика** — открытый остаток обязательств по статьям и по типу платежа на конец последних 6 месяцев, с индикатором роста/снижения (помесячный тренд — для точечного сравнения двух конкретных дат см. «Структура обязательств» выше).
7. **Приоритеты статей** — справочник статей: добавление новой статьи (название + тип по умолчанию), изменение типа для существующей, удаление статьи из списка (для каждой строки видно, сколько обязательств её сейчас используют — они после удаления не пострадают, просто статья пропадёт из выбора для новых обязательств). Тип статьи подставляется автоматически в форме ввода (см. ниже).
8. **Согласование** — видна и доступна только пользователям с ролью CEO/CFO (см. «Роли» ниже): очередь обязательств, ожидающих решения, чекбоксы + кнопка «Согласовать выбранное» для пакетного согласования реестра одним действием, кнопки «Согласовать»/«Отклонить» по одной записи (с необязательной причиной для отказа) и история решений.

## Ежедневный ввод

Форма «Новое обязательство» рассчитана на быстрый повторяющийся ввод оператором: поля в порядке **сумма → контрагент → статья**, Enter в сумме или контрагенте эквивалентен кнопке «Добавить», после сохранения статья и срок не сбрасываются (частый случай — несколько платежей подряд по одной статье за один день), а фокус возвращается в поле «Сумма». Тип платежа выбирать вручную не нужно — он подставляется по статье из справочника «Приоритеты статей» и виден в форме до сохранения (можно переопределить для конкретного платежа, если он выбивается из общего правила статьи).

## Модель приоритета: три уровня вместо да/нет

- **Базовые** — без этого бизнес останавливается (например, срочный транспорт под текущий рейс, налоги с риском блокировки счёта, зарплата, аренда).
- **Рост** — осознанные инвестиции в развитие (наём нового персонала, покупка оборудования для аренды): не критично сегодня, но это не утечка — деньги идут в дело.
- **Нерелевантные** — не относится к работе бизнеса; кандидат на сокращение в первую очередь, и именно это — источник данных для «Отчёта об утечках».

Список статей и их приоритет по умолчанию целиком живут в таблице `pay_category_priorities` — в коде инструмента ничего не захардкожено, добавлять/удалять статьи можно на вкладке «Приоритеты статей» без правки кода (см. «Экраны» выше). Статус «оплачено»/«частично» не хранится напрямую — вычисляется из фактических платежей (`pay_payments`), поле `status` в базе хранит только явную отмену (`cancelled`).

## Роли: оператор и согласующий (CEO/CFO)

Каждый сотрудник входит под своим отдельным логином (общий у всех инструментов компании — Supabase-проект, а не единый пароль на всех: логин/пароль у каждого свой, регистрируется самостоятельно или заводится администратором). Роль **зашита в токене пользователя** (`app_metadata.role` в `auth.users`) и приходит вместе с сессией в момент входа — известна сразу при авторизации, а не проверяется отдельным запросом к базе постфактум:

- **Оператор** (по умолчанию, ничего дополнительно настраивать не нужно) — вносит обязательства и оплаты в «Реестре», видит статус согласования каждой своей записи (badge «Ожидает» / «Согласовано» / «Отклонено», у отклонённых — причина), но вкладки «Согласование» не видит.
- **CEO/CFO** (согласующий, `role = 'approver'`) — дополнительно видит вкладку «Согласование»: очередь обязательств со статусом «Ожидает», согласование по одной записи или пакетом (чекбоксы + «Согласовать выбранное»). Как только решение принято, оператор увидит обновлённый статус в «Реестре» при следующем обновлении страницы.

Каждое новое обязательство создаётся со статусом `pending` («Ожидает»). Согласование не блокирует остальные экраны — обязательство сразу видно в «Структуре обязательств», «Очереди приоритизации», «Итогах периода», «Утечках» и «Динамике» независимо от статуса согласования; это отдельный контур контроля, а не шлюз для остальной аналитики.

**Назначить согласующего** — делает тот, у кого есть доступ к SQL Editor Supabase-проекта (это разовое действие для каждого нового CEO/CFO, ничего в интерфейсе инструмента для этого нет — намеренно, чтобы роль не мог выдать себе сам залогиненный пользователь):

1. Человек должен хотя бы раз войти в инструмент своим логином (чтобы завестись в `auth.users`).
2. В SQL Editor выполнить, подставив его логин:
   ```sql
   update auth.users
   set raw_app_meta_data = raw_app_meta_data || jsonb_build_object('role', 'approver')
   where email = '<логин>@opalubka.invalid';
   ```
3. Вкладка «Согласование» появится при следующем входе (уже открытая сессия подхватит роль не мгновенно — токен переиздаётся при обновлении сессии или повторном входе).

Снять роль (вернуть в операторы) — тот же запрос с `raw_app_meta_data - 'role'` вместо `||`. Права в базе на согласование намеренно не разграничены строже, чем у остальных действий инструмента (тот же принцип «доверяем всем залогиненным сотрудникам», что и в остальных инструментах DAYA — см. например коммит «Allow any authenticated user to delete periods» у инструмента СБ) — кнопки «Согласовать»/«Отклонить» скрыты в интерфейсе для не-согласующих, но это ограничение на уровне UI, не на уровне базы.

## Настройка базы (один раз)

Тот же Supabase-проект, что у остальных внутренних инструментов. В **SQL Editor** этого проекта выполнить [`supabase-setup.sql`](supabase-setup.sql) — скрипт идемпотентный, можно выполнять повторно.

## Вход

Тот же логин/пароль, что и в остальных внутренних инструментах компании (общий Supabase-проект, вход по логину без почты, синтетический email `логин@opalubka.invalid`).

## Что сознательно не сделано в этой версии

- **Пакетная загрузка файла** — только задел в схеме, форма не реализована.
- **Разграничение доступа только для финслужбы** — открыть инструмент может любой сотрудник с логином в общем Supabase-проекте компании, как и остальные внутренние инструменты; изнутри инструмента роли оператор/CEO-CFO уже есть (см. «Роли» выше), но входа именно для финслужбы отдельно от остальной компании нет.
- **Уведомления о новых обязательствах на согласование** — согласующий узнаёт о новых записях, только открыв вкладку «Согласование» (badge-счётчик рядом с названием вкладки виден сразу после входа); push/email-уведомлений нет.
